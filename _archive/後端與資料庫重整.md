# 後端與資料庫重整（2026-07-29）

> 三個後端：Firestore、GAS 檔案備份、Colab AI 批改。
> 結論先講：**Firestore 的結構不用改，但有四個地方漏了；GAS 併成一支；Colab 本來就已共用。**

---

## 一、Firestore：為什麼不改結構

現況是 `{學期}-progress` 這種前綴分法。另一種常見做法是 `progress/{學號}/terms/{學期}` 子集合。

不改的理由：

- 安全規則會變複雜（子集合要另寫一層 match，還要處理 collectionGroup）
- 教師端所有查詢都要改成 collectionGroup，成本高
- 既有資料要整批搬遷，開學前風險太大
- 前綴分法有個容易被忽略的優點：**學期結束後整包封存或刪除很單純**

所以結構維持不變，只修下面四件事。

## 二、四個實際的問題與處理

### ① 名冊兩份 → 合併成一份 `/roster`

`11501-roster` 與 `11502-roster` 裝的是同一批八年級學生。改名字、改驗證碼要改兩次，漏一次兩邊就對不起來。

**成績、進度必須分學期；但「人」不必。**

- `firestore.rules` 已新增 `/roster` 規則，舊的兩個移到「待淘汰」區
- 程式端不用改邏輯：`SSO.ROSTER` 已經是讀 `CONFIG.COLLECTIONS.ROSTER`，
  遷移完成後兩支 `config.js` 把該欄位改成 `'roster'` 即可

**遷移步驟（資料還沒動，以下是待辦）**

1. 先比對兩份名冊：學號、姓名、班級、座號、驗證碼有沒有不一致
2. 以驗證碼「已設定」的那一份為準寫入 `/roster`
3. 學生登入實測一次（快取鍵是 `sid{學期}`，兩學期各自獨立，不受影響）
4. 確認無誤後，刪掉 `firestore.rules` 的「D1 舊名冊」整段

> ⚠️ 別跳過第 1 步。驗證碼一旦覆蓋錯，學生就登不進去了。
> 需要的話可以做一支比對工具，列出兩邊差異再讓你決定取哪一份。

### ② 闖關紀錄改存進 `progress.history` —— 已完成

原本另開一個集合，而且兩學期命名還不一致：`quiz_records` 與 `quiz_records_115_2`，
兩者都躲在 `artifacts/school-quiz-app/public/data/` 這條早期範本留下的路徑底下。

改法：學生每次通關本來就會寫進 `{學期}-progress` 的 `history`，
證書需要的耗時與答對題數改由 `REPORT.unit()` 的 `extra` 一起寫進去。

```js
REPORT.unit('ethics', '5-2', {
  star: 3, score: 92,
  extra: { duration: '04:12', correct: 12, total: 13 }   // 只寫進 history
});
```

讀回來用 `REPORT.history('ethics', '5-2')`，由新到舊排序。

順帶處理的兩件事：

- `history` 加了長度上限（預設 400 筆），滿了會丟掉最舊的，避免單一文件無限長大
- 少一個集合、少一套安全規則，也不用再自動刪舊紀錄

**舊集合的規則暫時保留**，因為舊版 `cyberethics.html` / `social.html` 與教師端還在讀。
切換到新版頁面後，把 `firestore.rules` 的「D2」整段刪掉。

### ③ `{學期}-grades` 是死集合 —— 已刪

規則裡兩學期都有，但全站沒有任何一行程式讀寫它。已從 `firestore.rules` 移除。

### ④ appId 散了 5 個 —— 待處理

全站有 5 組不同的 appId 與 measurementId（各頁自己註冊了 Web App）：

```

1:85509938573:web:25a2f4459ab4b2c06771c4   G-J5Y45Z3XPW
1:85509938573:web:42329f883000089a6771c4   G-LEFNHXEKGS

1:85509938573:web:f02e73f85b86f9e06771c4   G-998D8NXNY1
```

你提供的共用設定要收斂成一組：


**要改的地方**：兩支 `config.js` 的 `FIREBASE` 換成新值，
然後把各頁那段 `Object.assign({}, window.CONFIG.FIREBASE, { appId: …, measurementId: … })`

> 代價是舊的 GA 資料流會斷在切換點，之後全站合成一條。

## 三、GAS：兩支部署 → 一支

### 舊的做法

兩個根資料夾、`TERM` 寫死在腳本裡，所以每學期必須各開一個 Apps Script 專案：

```
<截圖根>/11502/班級/座號/01.png
<作品根>/11502/班級/座號/03.sb3
```

腳本註解裡自己就寫著「本學期請另外開一個專案部署，不要覆蓋上學期那支」——
這正是漂移的來源：改一次要重新部署兩次。

### 新的做法（`_shared/filebackup.gs`）

單一根資料夾，中間多包一層「單元」，兩學期兩種檔案全部走同一套路徑：

```
<根> / 學期 / 單元 / 班級 / 座號 / 檔名

<根>/11501/thinking/801/05/03.png
<根>/11501/scratch/801/05/03.sb3
```

- 根資料夾 ID：`18q52AVJp3qWGOrqmWp0EKlmIT9mVzv3u`
- 學期由前端請求帶 `term`，但**只接受白名單**（`ALLOWED_TERMS = ["11501","11502"]`）
  漏傳或亂傳會被擋下並回報錯誤，不會靜悄悄寫進別的學期
- 兩支 `config.js` 的 `GAS_UPLOAD_URL` 填**同一個**部署網址

### 前端配合（已完成）

`11501_thinking.html` 與 `11502_thinking.html` 的上傳 payload 原本沒有帶 `term`，已補上：

```js
const payload = {
  term: window.CONFIG.TERM,     // ← 新增
  classRoom: user.classRoom,
  ...
};
```

Scratch 自評站本來就有帶，不用改。

### 部署與檢查

1. 開一個新的 Apps Script 專案，貼上 `shared/filebackup.gs`
2. 部署 → 新增部署作業 → 網頁應用程式
   執行身分「我自己」／存取權「任何人」
3. 用瀏覽器直接打開部署網址，`doGet` 會列出根資料夾名稱與兩學期的資料夾連結 ——
   **打開看到的路徑對不對，比等學生上傳失敗才發現好**
4. 兩支 `config.js` 的 `GAS_UPLOAD_URL` 換成新網址
5. 選用：在 Apps Script 編輯器手動執行 `createAllSeatFolders("11501")` 預建座號資料夾

> ⚠️ 舊資料還在舊的兩個根資料夾裡，新舊路徑不同。
> 要不要把舊檔搬進新結構，看你是否需要一次看完整學年。不搬也不影響上課。

## 五、共用檔清單（`_shared/`，由 `sync_shared.py` 同步）

| 檔案 | 說明 |
|---|---|
| `quiz-engine.js` | 章節測驗版型與流程 |
| `quiz-firebase.js` | 章節測驗的資料庫接線 |
| `sso.js` | 單一登入，學期由 `CONFIG` 推導 |
| `report.js` | 進度回報與 `history`，集合名由 `CONFIG` 推導 |
| `filebackup.gs` | GAS 檔案備份，一支服務兩學期 |
| `firestore.rules` | 安全規則（一個專案只有一份） |

> `firestore.rules` 是全系統唯一**刻意保留重複**的檔案：兩學期的規則明明一樣仍分開寫。
> 理由是安全規則寫錯的代價太高，用正規式合併雖然短，出事時很難一眼看出哪裡開太大。
> 其他檔案追求「一份程式」，這一份追求「一眼看得懂」。

**待手動處理**：兩個 repo 根目錄還留著舊的 `firestore.rules`，
現在的正本是 `shared/firestore.rules`，舊的請自行刪除以免日後改錯檔。
