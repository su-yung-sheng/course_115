# 後端安全性檢視（2026-07-29）

> 前提：身分維持「學號＋驗證碼」，不改用 Firebase Auth 真帳號。
> 優先順序依你的判斷：**冒用身分 ＞ 帳單風險 ＞ 成績篡改**。
>
> ⚠️ 先講結論：**先前的架構重整完全沒有動到安全模型**，只是把程式搬到共用位置，
> 漏洞原封不動跟著搬過去。這份文件是重整之後才做的第一次安全檢視。

---

## 一、根本限制（決定了什麼補得起來、什麼補不起來）

學生用**匿名登入**（`signInAnonymously`）。匿名帳號的 `uid` 每次都不同，
和學號沒有任何關聯，所以安全規則寫不出「只有本人能寫自己的資料」這種條件。

這一條限制直接造成下面 A、B 兩個漏洞**無法真正修好**，只能降低發生機率與傷害。
真正的解法只有一個：給學生真帳號（`學號@網域` 的 email/password），
規則就能寫成 `allow write: if request.auth.uid == sid`。你選擇暫不採用，這份文件依此假設撰寫。

## 二、漏洞清單

### ✅ A. 驗證碼形同虛設（**已修** 2026-07-29）

**問題**：登入流程是 `getDoc(roster/{學號})` 把整份名冊文件抓到前端，
再用 JavaScript 比對 `info.code`。而規則是 `allow get: if isSignedIn()` ——
學生是匿名登入，人人都算 signed in。

```js
// 任何學生在 Console 打這一行，就能讀到同學的姓名與驗證碼
(await getDoc(doc(db, '11502-roster', '14XXXXX'))).data()
// → { name: '...', cls: '801', no: '07', code: '123456' }
```

`allow list: if isTeacher()` 擋的是「一次撈全班」，但同學的學號本來就印在座號表上，
一個一個撈根本不需要暴力破解。

**核心問題**：驗證碼和它要保護的資料放在同一個文件裡，而學生讀得到那個文件。

**已採用的修法：把驗證碼搬到學生讀不到的地方，用「寫入試探」驗證**

關鍵是一個常被忽略的特性：**安全規則跑在伺服器端，`get()` 讀得到學生讀不到的文件。**

| 集合 | 內容 | 學生 | 老師 |
|---|---|---|---|
| `roster/{學號}` | 姓名／班級／座號＋`hasCode` 旗標 | 可讀單筆 | 可讀可寫 |
| `secret/{學號}` | **驗證碼本體** | ❌ 完全讀不到 | 可讀可寫 |
| `session/{學號}` | 登入試探 `{code, at}` | 只能寫 | 可讀 |

登入流程：

```js
// 寫得進去＝驗證碼正確；permission-denied＝錯誤
await setDoc(doc(db, SESSION, sid), { code: c, at: Date.now() });
```

規則自己去比對：

```
match /session/{sid} {
  allow read: if isTeacher();          // ❌ 學生不可讀，否則等於換個地方外洩
  allow create, update: if isSignedIn()
    && loginShapeOk()
    && request.resource.data.code ==
       get(/databases/$(database)/documents/secret/$(sid)).data.code;
}
```

學生仍然可以自訂驗證碼（`secret` 只開放 `create`，天然只能設定成功一次），
但從頭到尾讀不到任何人的驗證碼，包括自己的。

**為什麼不用雜湊**：雜湊之後你查不到學生忘記的驗證碼，只能重設。
管幾百個學生時這個代價不划算，所以選了「老師看得到、學生看不到」的做法。

**還沒解決的**：搶先替尚未登入的同學設定驗證碼 —— 但這在改版前也一樣，沒有變差。
要防這個得由你先批次匯入初始驗證碼，學生首次登入時用它換成自己的。

**改到的檔案**：兩支 `hub.html`（登入與首次設定）、兩支 `teacher.html`（名冊驗證碼管理）、
兩支 `config.js`（新增 `SHARED` 集合名稱）、`_shared/firestore.rules`，
以及一次性轉換工具 `course_11502/migrate.html`。

### 🟡 B. 進度可以互相覆寫（已降低傷害，無法根治）

**問題**：`{學期}-progress/{sid}` 原本是 `allow create, update: if isSignedIn()`，
完全沒有比對 `sid` 是不是自己。任何學生可以寫任何人的成績文件。

**已修（規則層）**：加了兩道限制。

```
allow create: if isSignedIn() && firstWriteIsSmall();          // 第一次寫入 ≤ 6 星
allow update: if isTeacher()
              || (isSignedIn() && starsNotReduced() && gainIsSmall());
```

- `starsNotReduced()` —— **星星不可以變少**。擋掉「把別人的進度清成 0」這種
  最惡意、也最難救回來的破壞。
- `gainIsSmall()` —— **單次最多加 6 顆星**。單次通關最多給 3 顆，放寬到 6 正常上課不會踩到。
  擋掉「一次改成滿星」。

老師以 email/密碼登入，`isTeacher()` 為真，不受這兩條限制 ——
教師端的「清進度」照常可用。

**還是擋不住**：有耐心的學生仍可以每次 +6、慢慢灌水，或小幅度改別人的分數。
要根治只能改用真帳號。

### ✅ C. 批改紀錄可被任何人新增（**已修** 2026-07-29）

`{學期}-scratch-submissions` 原本是 `allow create: if true` —— **連登入都不用**。
這不只是竄改問題：任何人知道 projectId 就能無限寫入你的 Firestore，帳單算你的。
`{學期}-grader` 原本也是 `allow read: if true`。

原因是 Colab 後端用「未登入的 REST（只帶 api_key）」讀寫 Firestore，規則只好整個開著。

**已修**：後端改為匿名登入取得 `idToken`，之後每次 REST 請求都帶
`Authorization: Bearer <idToken>`，規則就能收成 `if isSignedIn()`。

改動在 `11502_backend.ipynb` 的核心模組（步驟 2 那格）：

| 新增 | 作用 |
|---|---|
| `_fs_signin()` | 匿名登入取得 idToken（有效期約 1 小時） |
| `_fs_refresh()` | 用 refreshToken 續期，長時間上課不會中途失效 |
| `_fs_token()` | 取可用權杖；失敗時回空字串，退回未登入模式而不是整個掛掉 |
| `_fs_http()` | 自動帶上權杖；遇到 401/403 會清掉權杖重登一次再試 |

版本號同步改為 `2026-07-29-fsauth`，`features` 加入 `fs_auth`，
兩支 `config.js` 的 `BACKEND_FEATURES` 也加了同一項 ——
**這樣 Colab 若跑的是舊 notebook，教師端會直接提示你重新執行**，
不會出現「規則收緊了但後端還是舊的」而全班批改失敗。

⚠️ 前提：Firebase Console → Authentication → 登入方式，**「匿名」必須是啟用的**
（學生端本來就用匿名登入，所以通常已經開著）。

> 順帶發現：後端的 `/api/teacher/submissions` 端點會 list 整個 submissions 集合，
> 但規則是 `read: if isTeacher()`，所以**這個端點在改版前就已經是失敗的**。
> 全站沒有任何頁面呼叫它，屬於死端點，維持現狀即可。
> 日後若真要看批改紀錄，讓教師端直接讀 Firestore 比較單純（它本來就以老師身分登入）。

### 🟢 D. GAS 上傳沒有任何驗證（已降低風險）

部署設定是「任何人」且腳本不檢查身分，知道網址就能往你的雲端硬碟丟檔案。

**已修**：`shared/filebackup.gs` 加了三道檢查。

| 檢查 | 作用 |
|---|---|
| `checkKey()` | 請求要帶 `key`，與 Apps Script 指令碼屬性的 `UPLOAD_KEY` 比對 |
| `checkSize()` | 單檔上限 15 MB，擋掉誤傳大檔或灌爆硬碟 |
| `checkTerm()` | 學期白名單，擋掉寫進錯誤的學期資料夾 |

前端已配合：兩支 `config.js` 加了 `GAS_UPLOAD_KEY`，
兩支 `thinking.html` 與 Scratch 自評站的 payload 都帶上 `key`。

**要做的設定**（沒設就等於不檢查，方便你先部署再補）：

```
Apps Script 編輯器 → 專案設定 → 指令碼屬性 → 新增
   屬性：UPLOAD_KEY
   值：  c115-upload      ← 與 config.js 的 GAS_UPLOAD_KEY 一致
```

設好之後，用瀏覽器打開部署網址，回應裡的 `keyRequired` 會變成 `true`。

> ⚠️ 誠實說明：`key` 寫在前端 JS，學生按 F12 就看得到。
> 它擋的是**不知道網址與 key 的外人隨機掃描**，不是擋你的學生。
> 但這正是「帳單風險」的主要來源，所以仍然值得做。

## 四、上線步驟（順序不能顛倒）

1. **先發佈新的安全規則**
   Firebase Console → Firestore → 規則 → 貼上 `shared/firestore.rules` → 發佈
   （規則裡舊的 `{學期}-roster` 還在「待淘汰」區，所以此時舊頁面仍然能用）

2. **執行轉換**
   打開 `course_11502/migrate.html` → 教師登入 →
   **① 掃描並預覽**（把紅色的衝突列逐筆看過）→ **② 執行轉換** → **③ 驗證結果**

   > 舊集合不會被刪除，出事可以退回去。

3. **切換名冊來源**
   兩支 `config.js` 的 `COLLECTIONS.ROSTER` 改成 `'roster'`。
   另外這兩處還寫死著舊集合名，要一起改：
   - `11501_cyberethics.html` 的 `const ROSTER_COL = '11501-roster'`
   - 兩支 `teacher.html` 的 `const COL = '{學期}-roster'`

4. **用一個學生帳號實際登入測試**
   - 已設過驗證碼的：輸入正確碼要能進、輸入錯碼要顯示「驗證碼錯誤」
   - 沒設過的：要能進入首次設定畫面並自訂成功
   - 教師端名冊：驗證碼要看得到、改得動、清得掉

5. **重新執行 Colab notebook**（★ 順序很重要）
   規則裡的 `grader` 與 `scratch-submissions` 已經收成 `if isSignedIn()`，
   **舊版後端（未登入 REST）會讀不到批改標準**。發佈規則後務必重跑 notebook。

   確認方式：開教師端的「🩺 狀態檢查」，或直接看 `/api/health` 的
   `version` 是不是 `2026-07-29-fsauth`、`features` 有沒有 `fs_auth`。
   若跑的是舊版，教師端會主動提示你重新執行。

6. **Apps Script 設定 `UPLOAD_KEY`**，再實測一次截圖與作品上傳；
   打開 GAS 部署網址確認 `keyRequired: true`、`rootName` 是你的資料夾

7. **確認一週沒問題後**，刪除舊的 `11501-roster` / `11502-roster`、
   規則裡的「D1 舊名冊」整段，以及 `migrate.html`
