# 05 · 安全性

> 誠實版。這裡寫的是**擋得住什麼、擋不住什麼**，不是「已經很安全了」。

---

## 1. 根本限制

學生用**匿名登入**（`signInAnonymously`）。匿名帳號的 `uid` 每次都不同，
和學號沒有任何關聯，所以安全規則寫不出「只有本人能寫自己的資料」。

真正的解法只有一個：給學生真帳號（`學號@網域` 的 email/password），
規則就能寫成 `allow write: if request.auth.uid == sid`。
目前**刻意不採用**，因為登入流程要改、忘記密碼要老師重設，成本大於收益。

這條限制直接決定了下面哪些補得起來、哪些補不起來。

---

## 2. 驗證碼：已修

### 原本的問題

登入流程是 `getDoc(roster/{學號})` 把整份名冊文件抓到前端，再用 JavaScript 比對 `info.code`。
規則是 `allow get: if isSignedIn()` —— 學生是匿名登入，人人都算 signed in。

```js
// 改版前：任何學生在 Console 打這一行，就能讀到同學的姓名與驗證碼
(await getDoc(doc(db, '11502-roster', '14XXXXX'))).data()
// → { name: '...', cls: '801', no: '07', code: '123456' }
```

`allow list: if isTeacher()` 擋的是「一次撈全班」，但同學的學號印在座號表上，
一個一個撈根本不需要暴力破解。**鎖和鑰匙放在同一個抽屜。**

### 現在的做法

關鍵：**安全規則跑在伺服器端，`get()` 讀得到學生讀不到的文件。**

| 集合 | 內容 | 學生 | 老師 |
|---|---|---|---|
| `roster/{學號}` | 姓名／班級／座號 ＋ `hasCode` 旗標 | 可讀單筆 | 可讀可寫 |
| `secret/{學號}` | **驗證碼本體** | ❌ 完全讀不到 | 可讀可寫 |
| `session/{學號}` | 登入試探 `{ code, at }` | 只能寫 | 可讀 |

登入 = 往 `session` 寫一筆，寫得進去就是對的：

```js
await setDoc(doc(db, SESSION, sid), { code: c, at: Date.now() });
// 成功 → 通過；permission-denied → 驗證碼錯誤
```

```
match /session/{sid} {
  allow read: if isTeacher();          // ❌ 學生不可讀，否則等於換個地方外洩
  allow create, update: if isSignedIn()
    && loginShapeOk()
    && request.resource.data.code ==
       get(/databases/$(database)/documents/secret/$(sid)).data.code;
}
```

學生仍然可以自訂驗證碼（`secret` 只開放 `create`，天然只能設定成功一次），
但從頭到尾讀不到任何人的驗證碼，包括自己的。

### 為什麼不用雜湊

雜湊之後**老師也查不到學生忘記的驗證碼**，只能重設。
管幾百個學生時這個代價不划算，所以選了「老師看得到、學生看不到」。

### 還沒解決

**搶先替尚未登入的同學設定驗證碼** —— 改版前也一樣，沒有變差。
要防這個得由老師先批次匯入初始驗證碼，學生首次登入時用它換成自己的。

## 3. 進度篡改：只能降低傷害

`{學期}-progress/{sid}` 沒有辦法驗證「這個 sid 是不是你」。規則只能限制**動作幅度**：

```
allow create: if isSignedIn() && firstWriteIsSmall();          // 第一次寫入 ≤ 6 星
allow update: if isTeacher()
              || (isSignedIn() && starsNotReduced() && gainIsSmall());
```

| 規則 | 擋掉什麼 |
|---|---|
| `starsNotReduced()` | 把別人的星星清成 0（最惡意、最難救的破壞） |
| `gainIsSmall()` | 一次改成滿星（單次通關最多 3 顆，放寬到 6） |

老師以 email/密碼登入，`isTeacher()` 為真，不受限制 —— 教師端「清進度」照常可用。

**擋不住**：有耐心的學生仍可每次 +6 慢慢灌水，或小幅度改別人的分數。

## 4. 後端存取：已收緊

`{學期}-grader` 的 `read` 與 `{學期}-scratch-submissions` 的 `create`
原本都是 `if true` —— **連登入都不用**。這不只是竄改問題：
任何人知道 projectId 就能無限寫入你的 Firestore，帳單算你的。

Colab 後端改為匿名登入帶 `idToken` 後，兩者都收成 `if isSignedIn()`。
把「全世界」縮小成「有登入的人」，隨機掃描與外部灌爆就擋掉了。

> 順帶一提：後端的 `/api/teacher/submissions` 端點會 list 整個 submissions 集合，
> 但規則是 `read: if isTeacher()`，所以**這個端點在改版前就已經是失敗的**。
> 全站沒有任何頁面呼叫它，屬於死端點。

---

## 5. GAS 上傳：已降低風險

部署設定是「任何人」且腳本不檢查身分，知道網址就能往雲端硬碟丟檔案。
現在加了通行碼、檔案大小上限、學期白名單（見 [04](04_後端與資料庫.md)）。

⚠️ **誠實說明**：`key` 寫在前端 JS，學生按 F12 就看得到。
它擋的是**不知道網址與 key 的外人隨機掃描**，不是擋你的學生。
但這正是「帳單風險」的主要來源，所以仍然值得做。

## 6. 無解的部分

| 項目 | 說明 |
|---|---|
| 班級密碼公開 | `CLASS_PASS` 明寫在 `config.js`。任何放在純前端的密碼都是如此 |
| Firebase apiKey 公開 | 這是設計如此，不是機密。真正的保護是安全規則 |
| 進度可互相覆寫 | 見第 3 節，要根治只能改用真帳號 |
| 匿名帳號累積 | Colab 每次重啟產生一個新匿名帳號。不影響運作，介意的話可定期清理 |

## 7. 規則檔的閱讀順序

`shared/firestore.rules` 分成五區：

| 區 | 內容 |
|---|---|
| A | 跨學期共用：`roster` / `secret` / `session` |
| B | 上學期 `11501-*` |
| C | 下學期 `11502-*`（與 B 規則相同，僅集合名不同） |
| D | **待淘汰**：舊名冊、舊闖關紀錄、各頁自有集合 |
| E | 其他一律拒絕 |

D 區是給過渡期用的。舊版頁面全部下線後，整區刪掉。
