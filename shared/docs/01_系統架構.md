# 01 · 系統架構

> 一套程式碼，兩個學期。學期只是資料。

---

## 1. 為什麼要這樣改

2026-07 之前，上下學期是兩份 fork 出來的程式碼。結果就是持續漂移：

- `guard.js` 兩份**一個字都沒差**、`firestore.rules` 兩份完全相同
- `grading.js` 只差註解裡的學期編號
- `theme.css`、`report.js` 只有下學期有；`status.html`、`check.py` 只有上學期有
- 逐行比對：`hub` 90% 相同、`teacher` 88%、`thinking` 68%

**內容分兩學期是對的，但程式碼被複製成兩份才是問題根源。**
所有已知落差都出自「改一邊漏另一邊」。

---

## 2. 現在的切法

界線不是「上學期／下學期」，而是：

| 層 | 放什麼 | 位置 |
|---|---|---|
| **機制** | 登入、守門、計分、進度回報、版型引擎、後端 | `shared/` |
| **設定** | 學期、集合名稱、班級密碼、單元清單 | `{學期}/config.js` |
| **內容** | 章節、教材、題庫 | `{學期}/content/` |
| **頁面** | 各教材頁 | `{學期}/*.html` |

### `shared/` 內容一覽

| 檔案 | 用途 |
|---|---|
| `guard.js` | 身分守門：沒從闖關基地登入就導回入口 |
| `sso.js` | 單一登入：身分由入口帶入，學期從 `CONFIG` 推導 |
| `grading.js` | 星等門檻的單一來源 |
| `report.js` | 進度回報與 `history`，集合名從 `CONFIG` 推導 |
| `theme.css` | 全站配色與版型的單一來源 |
| `quiz-engine.js` | 章節測驗的版型與流程（畫面 100% 由它產生） |
| `quiz-firebase.js` | 章節測驗的資料庫接線 |
| `status.html` | 上課前的系統狀態檢查頁 |
| `template.html` | 新增頁面用的空白範本 |
| `check.py` | 推送前的檔案完整性檢查 |
| `backend.ipynb` | Colab AI 批改後端（★ 兩學期共用一本） |
| `filebackup.gs` | Google Apps Script 檔案備份（★ 一支部署服務兩學期） |
| `firestore.rules` | Firestore 安全規則（一個專案只有一份） |
| `docs/` | 這幾份文件 |

## 3. 沒有同步機制（這是好事）

`shared/` 只有一份，`11501/` 與 `11502/` 用 `../shared/xxx.js` 直接引用。

這一版之前曾經是「兩個 repo + `_shared/` 原始碼 + `sync_shared.py` 同步 + 防呆檢查」，
那整套機制存在的唯一理由，是兩個 repo 沒辦法共用檔案。
併成一個 repo 之後：**沒有副本 → 不會不同步 → 不需要同步腳本，也不需要防呆。**

唯一還保留的守門是 `shared/check.py`（由 git 的 pre-commit hook 觸發），
它擋的是死連結、語法錯誤、名冊設定不一致這類問題，與同步無關。

## 4. 版型引擎：內容不同、外觀相同

以章節測驗為例。上學期教資訊倫理、下學期教媒體與社會議題，**內容完全不同，但流程一模一樣**：
章節選單 → 整章測驗 → 依最佳正確率給星 → 回報進度。

所以做成「一份引擎 + 兩份內容資料」：

```
shared/quiz-engine.js       545 行，版型與流程，兩學期共用
11501/content/ethics.js     上學期：3 章、10 個可挑戰項目
11502/content/social.js     下學期：2 章、10 個可挑戰項目
{學期}/cyberethics_new.html · social_new.html   各 29 行的外殼
```

原本各 1200 行的兩支頁面，變成各 29 行的外殼。
**兩學期唯一不同的一行是 `<script src="content/xxx.js">`。**

外殼長這樣：

```html
<script src="config.js"></script>
<script src="../shared/guard.js"></script>
...
<script src="content/social.js"></script>             <!-- 教什麼 -->
<script src="../shared/sso.js"></script>
<script src="../shared/grading.js"></script>
<script src="../shared/report.js"></script>
<script src="../shared/quiz-engine.js"></script>      <!-- 長什麼樣、怎麼跑 -->
<script type="module" src="../shared/quiz-firebase.js"></script>
```

內容資料格式：

```js
window.QUIZ_CONTENT = {
  moduleId: 'ethics',            // 進度回報用的模組代號
  color: 'pink',                 // 主色，對照《設計規範》模組代表色
  target: 10, maxWrong: 20,      // 目標連對、容錯上限
  chapters: [{
    id: 'ch5', title: '第五章 …', color: 'pink', pdf: 'https://…',
    challenge: { id:'5-all', notes:'…', questions:[…] },   // 整章挑戰，可省略
    sections: [
      { id:'5-1', title:'5-1 …', notes:'<h4>…</h4>', questions:[{q, options, correct}] }
    ]
  }]
};
```

整章挑戰若不給 `questions`／`notes`，引擎會自動合併小節的題庫與教材。

|---|---|---|
| `hub.html` | 90% | 模組卡片清單、關卡數、色系 |

## 5. 為什麼併成一個 repo

原本是兩個 repo、兩個 GitHub Pages 網址。那樣做的代價是共用檔必須「一份原始碼 + 兩份副本 + 同步腳本」，
而同步這件事本身就是新的出錯來源。

併成一個之後：

- `shared/` 只有一份，改一次兩學期同時生效，不可能漏
- 少了 `sync_shared.py` 與相關的防呆檢查
- 網址變成 `/course_115/11501/` 與 `/course_115/11502/`，總入口 `/course_115/` 依日期導向

代價是兩學期綁在同一個 repo、同一個 Pages 站台。以這套系統的規模來說，這個代價遠小於同步的成本。

---

## 6. 刻意保留的重複

`firestore.rules` 裡兩學期的規則明明長得一樣，仍然分開寫。

理由：安全規則寫錯的代價太高。用正規式把 `11501`／`11502` 合成一條雖然短，
但出事時很難一眼看出哪裡開太大。**其他檔案追求「一份程式」，這一份追求「一眼看得懂」。**
